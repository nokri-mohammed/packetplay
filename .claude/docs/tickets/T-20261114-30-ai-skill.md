## Spec

### 1. Single-file build

- New `scripts/build-skill.ts` and script `"build:skill": "bun run scripts/build-skill.ts"`. It writes
  `skills/packetplay/packetplay.js` (a bundled, minified file that runs with `bun
  skills/packetplay/packetplay.js <command>`) by embedding the three things above:
  - generate (at build time, git-ignored file such as `src/generated/embedded.ts`) a module exporting
    the pre-bundled player JS text, a map of icon name to SVG text, and the schema JSON object; make
    `page.ts`, `icons.ts` and `validate.ts` use the embedded data when that module is present and fall
    back to the current disk and `Bun.build` code otherwise (for example through a small
    `src/embedded.ts` indirection that the bundler replaces; choose the simplest approach that leaves the
    dev path and tests exactly as they are);
  - bundle `src/cli.ts` with `Bun.build` (`target: "bun"`, minify) into the single file with a
    `#!/usr/bin/env bun` first line. `ajv` and `yaml` are bundled in.
- The built file is committed (so the skill works from a plain clone) and rebuilt by the script.
  Add `skills/packetplay/packetplay.js` to the repo, keep generated intermediate files git-ignored.
- Proof it is self-contained: run it from a temporary directory outside the repo with only the example
  scene copied in (a throwaway directory under the OS temp area, not committed) and compare its output
  with the dev CLI's output for the same scene: the two HTML files must be byte-identical (state the
  sizes). Do this for all five examples.
- Report the real size of `packetplay.js`.

### 2. Three small CLI commands (also useful without the skill)

- `packetplay validate <file>`: loads and validates, prints `ok: <title> (N nodes, M steps)` and exits 0,
  or prints the problems (the existing messages, one per line) and exits 1. Writes no HTML.
- `--json` flag for `validate` and `build`: on failure print one JSON object `{ "ok": false, "issues":
  [ { "message": string, "path"?: string } ] }` to stdout (exit 1), on success `{ "ok": true, "title":
  string, "nodes": n, "steps": n, "out"?: string }`. Keep the exact existing human messages inside
  `message`. Without `--json` nothing changes.
- `packetplay icons`: prints the icon names, one per line (the 37 vendored isoflow icons).
- Update the usage text and add exact tests (exit codes and output) for all three; the existing CLI
  tests stay green.

### 3. The skill folder

`skills/packetplay/SKILL.md` with YAML frontmatter `name: packetplay` and a `description` (one or two
sentences, trigger words: diagram, animated, packet, network flow, how X works, scene file, OSI, DNS)
saying when to use it. The body (about 120 lines at most, plain English, no em dashes):
1. Workflow: write `<name>.scene.yaml` next to where the user works, run `bun <skill dir>/packetplay.js
   validate <file> --json`, fix every issue, then `build <file> -o <name>.html`, tell the user where the
   file is. (Say the skill directory is the folder that holds this `SKILL.md`.)
2. Scene format cheat sheet (from the schema): `version: 1`, `title`, `nodes` (icon from `packetplay
   icons`, `label`, `sub`, `group`, `at`, `hidden`), `links`, `groups`, `tracks` (colours), `chapters` and
   `steps` (`from` and `to` must differ, `label`, `desc`, `data` at most 4 keys, `at` per node with
   `set`/`desc` for NAT-like rewrites, `mode: flow`, `both`, `parallel`, `reveal`, `typing`).
3. Rules the AI gets wrong: quote YAML values that look like booleans or numbers; no `: ` inside an
   unquoted `desc`; use documentation addresses (`192.0.2.x`, `198.51.100.x`, `203.0.113.x`,
   `example.com`) never real ones; only the vendored icons; hidden nodes must be revealed before use.
4. A pointer to `examples/` (copy the five example scenes into `skills/packetplay/examples/`, YAML only)
   and when to use which (UDP: small; website: hidden, typing, NAT; OSI: groups; homenet: explicit `at`;
   WebRTC: flows and parallel).
5. How to see it: open the HTML in a browser; controls (Play/Pause, Restart, speeds 0.5x to 2x, keys).
- Keep the skill files free of absolute local paths.
- README: a short "Use as a Claude skill" section with the exact steps: `bun run build:skill`, then `ln -s
  <path to this repo>/skills/packetplay ~/.claude/skills/packetplay` (or copy the folder into a
  project's `.claude/skills/`), Bun required, how to ask, how to update (rebuild; the symlink follows).
  Use a placeholder like `<path to this repo>`, never a real path.
- Tests: `skills/packetplay/SKILL.md` has the frontmatter `name: packetplay` and a non-empty description,
  contains no em dash and no `/home/`; every example in `skills/packetplay/examples/` validates with
  `validateScene`; `packetplay.js` exists, starts with the shebang, and `bun skills/packetplay/packetplay.js
  --help` exits 0 (smoke test, run in the test through `Bun.spawn`).

**Lessons.**
- A Bun build plugin with `onLoad` on a tiny indirection module (`src/embedded.ts`) embeds data into a
  single file with no generated file and no change to the dev path; the player text is the same
  `Bun.build` output, so pages are byte-identical by construction.
- Bun re-emits the entry's shebang, so the bundle only needs a chmod.
- In a test, write a forbidden character such as the em dash as `String.fromCharCode(0x2014)`; a literal or
  `\u` escape in a written file can end up as the real character and trip the repo's own no-em-dash check.
- `SKILL.md` examples text must match the example files (webrtc has flow steps, parallel is in homenet).
